# Справочник организаций-покупателей — дизайн

Дата: 2026-07-22
Статус: одобрен пользователем, готов к написанию implementation plan

## Проблема

Сейчас данные покупателя (`buyer_group`: Organization, NIP, Country, Street, City,
Postal Code) — это ACF-поля на самой фактуре (`facture_group.buyer_group`),
заполняемые вручную при каждом создании фактуры. Отдельного справочника
контрагентов нет: список организаций для фильтра в Margin Report
(`Margin_FSFacture::get_buyer_organization_groups()`) каждый раз вычисляется
на лету перебором всех фактур.

Главная боль: при создании новой фактуры менеджер каждый раз вручную
перепечатывает данные организации, если она уже выставляла счета раньше.
Из-за этого одна и та же организация может попадать в разные фактуры
с опечатками/расхождениями в написании.

## Цель этой задачи

Дать менеджеру возможность выбрать организацию из справочника при создании
фактуры и автоматически подставить её данные в текстовые поля `buyer_*`.

Данные в фактуре остаются собственным снапшотом (как сейчас) — редактируемым,
без обратной синхронизации со справочником.

## Явно вне рамок (Non-goals)

- Миграция старых фактур: их `buyer_group` не трогаем, связь с новым
  справочником им не проставляем.
- Margin Report: продолжает строить список организаций из данных фактур
  (`get_buyer_organization_groups()`), как сейчас. Переключение фильтра
  отчёта на справочник — отдельная будущая задача.
- `KSeF_XML_Builder.php`: обнаруженное расхождение с `XML_FSFacture.php`
  (старый билдер игнорирует `buyer_street/city/postal_code/country_code`,
  шлёт весь адрес одной строкой и хардкодит `KodKraju = 'PL'`) —
  фиксируется как известная проблема, не устраняется в рамках этой задачи.
- Создание организации "на лету" прямо из формы фактуры — только через
  отдельный экран администрирования.
- Автоматическое обновление уже существующих записей справочника при
  повторном импорте — существующие записи не перезаписываются.

## Модель данных

Новый CPT `fs_organization`, регистрируется по образцу `factures`
(`App_FSFacture::init_app()`):

```php
register_post_type('fs_organization', [
    'labels'             => [ /* Organization/Organizations, аналогично labels у 'factures' */ ],
    'public'             => false,
    'publicly_queryable' => true,
    'show_ui'            => true,
    'show_in_menu'       => true,
    'capability_type'    => 'post',
    'has_archive'        => false,
    'menu_icon'          => 'dashicons-building',
    'supports'           => ['title'],
    'show_in_rest'       => true,
]);
```

`post_title` = название организации (используется для поиска в select2
Post Object поля).

ACF-группа `fs_organization_group` (создаётся через ACF UI в WP-админке,
как и текущая группа `facture_group`), привязанная к CPT `fs_organization`:

| Поле                | Тип  | Соответствие в фактуре       |
|---------------------|------|-------------------------------|
| `org_nip`            | text | `buyer_nip`                   |
| `org_country_code`   | text | `buyer_country_code`          |
| `org_street`         | text | `buyer_street`                |
| `org_city`           | text | `buyer_city`                  |
| `org_postal_code`    | text | `buyer_postal_code`           |

## Экран администрирования

Стандартный список записей CPT (колонки: Name, NIP, City, Country) и
стандартная ACF-форма редактирования. Доступ — `edit_posts` (как у Margin
Report). Пункт меню — на верхнем уровне (аналогично Factures), либо
подпунктом — решается на этапе реализации по месту.

На экране списка — кнопка **"Import from factures"** (см. раздел «Импорт»).

## Интеграция с формой фактуры

В ACF-группу `facture_group.buyer_group` добавляется новое поле
`buyer_organization_ref` типа **Post Object**, `post_type = fs_organization`,
одиночный выбор (select2). Располагается над существующими текстовыми
полями `buyer_organization`, `buyer_address`/`buyer_street`, `buyer_city`,
`buyer_postal_code`, `buyer_nip`, `buyer_country_code` — которые остаются
без изменений (тип, имена, поведение).

## Автоподстановка данных

Реализуется по образцу уже существующего механизма для товаров
(`ACF_FSFacture::wp_ajax_acf_get_product_data_handle()` +
`assets/acf/product/product.js`):

1. Новый JS-файл `assets/acf/organization/organization.js`, подключается
   на экране редактирования фактуры (по аналогии с `product.js`).
2. Слушает `change` на `.acf-field[data-name="buyer_organization_ref"] select`.
3. По AJAX (`action: 'fs_facture_get_organization_data'`, новый обработчик
   в классе, отвечающем за фактуры/ACF) запрашивает данные организации по
   её ID.
4. PHP-обработчик читает ACF-поля `fs_organization_group` записи и
   возвращает `wp_send_json_success([...])` с полями
   `organization, nip, country_code, street, city, postal_code`.
5. JS находит соседние ACF-поля внутри `buyer_group` (по `data-name`) и
   проставляет туда значения через `.val(...)`.
6. Дальше поля обычные — редактируются вручную, без связи с
   `buyer_organization_ref` (одноразовое одностороннее заполнение).

## Импорт существующих организаций из фактур

Кнопка **"Import from factures"** на экране списка `fs_organization`
запускает AJAX-обработчик, который:

1. Проходит по всем фактурам и группирует покупателей по тому же ключу,
   что и сейчас в `Margin_FSFacture::get_buyer_group_key()`:
   NIP (приоритет) → иначе нормализованное название организации.
2. Для каждой группы берёт данные (`buyer_organization`, `buyer_nip`,
   `buyer_country_code`, `buyer_street`, `buyer_city`, `buyer_postal_code`)
   **из самой свежей по дате фактуры** этой группы.
3. Проверяет, есть ли уже запись `fs_organization` с таким же ключом
   (NIP/нормализованное название). Если есть — пропускает (**не
   перезаписывает** существующую запись, чтобы не затереть ручные правки).
   Если нет — создаёт новую запись CPT с заполненными ACF-полями.
4. Возвращает сводку: `created: N, skipped: M`.
5. Идемпотентно — можно запускать повторно по мере появления новых
   покупателей в фактурах.

### Рефакторинг для устранения дублирования

Логика ключа группировки (`get_buyer_group_key`, `normalize_organization_label`,
`normalize_organization_key`, `clean_tax_id`) сейчас существует только как
приватные методы `Margin_FSFacture`. Поскольку она нужна теперь в двух
местах (Margin Report и импортёр организаций), выносится в общий класс
`src/Buyer_Data_Helper.php` (статические методы или трейт). `Margin_FSFacture`
переводится на использование этого хелпера вместо своих приватных копий
(поведение Margin Report не меняется, это чисто структурный рефакторинг).

## Обработка ошибок / граничные случаи

- Организация без NIP (только название) — группируется/импортируется по
  нормализованному названию, как и сейчас в Margin Report.
- Пустые/отсутствующие поля адреса в исходной фактуре — переносятся в
  справочник как есть (пустая строка), менеджер дозаполняет вручную.
- Повторный импорт после ручного редактирования записи в справочнике —
  запись не трогается (см. non-goals).
- Права доступа: AJAX-обработчики (автоподстановка и импорт) проверяют
  `current_user_can('edit_posts')`, как остальные AJAX-хендлеры плагина.

## Тестирование (вручную)

1. Активировать плагин, убедиться что CPT `fs_organization` и пункт меню
   появились.
2. Создать ACF-группу `fs_organization_group` в UI, создать 2-3 тестовые
   организации вручную.
3. Открыть форму новой фактуры, выбрать организацию в
   `buyer_organization_ref` — убедиться, что текстовые поля `buyer_*`
   заполнились корректно и остаются редактируемыми.
4. Сохранить фактуру, убедиться, что PDF и XML-экспорт (`XML_FSFacture.php`)
   генерируются как обычно, без регрессий.
5. Нажать "Import from factures" на пустом справочнике (или с несколькими
   существующими записями) — проверить, что создались записи для
   уникальных покупателей из старых фактур, дубли не создались, сводка
   created/skipped корректна.
6. Запустить импорт повторно — убедиться, что ничего не задублировалось и
   существующие записи не изменились.
7. Убедиться, что Margin Report продолжает работать без изменений
   (список организаций для фильтра не зависит от нового CPT).

## Известные проблемы, зафиксированные, но не устраняемые здесь

- `KSeF_XML_Builder.php` не использует `buyer_street/city/postal_code/country_code`
  и хардкодит `KodKraju = 'PL'`, в отличие от `XML_FSFacture.php`. Реальная
  отправка в KSeF идёт через `KSeF_XML_Builder.php` (`KSeF_FSFacture.php:547`).
  Пользователь решил не трогать это в рамках текущей задачи.
